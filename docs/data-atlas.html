Schema reference

Every table in Mail Orbyt, and why it exists

One Postgres database, one schema file, 62 tables and 30 enums, organised the way the product actually moves: a lead comes in, gets researched, gets a drafted email, gets enrolled in a campaign, gets sent, gets opened or replied to, and — sometimes — becomes a meeting. Every section below follows that order.

Engine PostgreSQL 16, one schema, no sharding Tenancy every business-data row carries organisationId Client Prisma ORM (packages/database)

A reply is the one event that overrides everything: Conversation is keyed by (org, lead, inbox) rather than by campaign, and a genuine reply exits every active enrollment for that lead — not just the campaign that sent it. Suppression (§7) and the AI-boundary rule (research is deterministic, only drafting uses AI) both apply throughout this flow but aren't shown as nodes since they're gates, not steps.

15 · Logs, outside the database

Two different things both get called "logs" here, and it's worth keeping them straight:

WhatWhere it livesWhat it's for
AuditEvent (§3)Postgres, queryable with SQLSecurity/compliance history — who did what, permanently kept
Structured JSON logsstdout → pm2 → ~/.pm2/logs/<app>-{out,error}.log on each VPSOperational tracing (request handling, worker ticks, job failures) — not queryable, rotated/ephemeral

The app logger (packages/logging) emits one JSON line per event with service, level, message, and context fields, and automatically redacts anything that looks like a token or secret before it's written. On orbytflow-vps, tail it live with pm2 logs mail-orbyt-worker, or read a specific file directly.

16 · Connecting a query tool

You're running this for several businesses, each with its own Postgres on its own VPS. The one thing worth fixing before picking a tool: don't connect to a database port directly over the internet. Every one of the options below supports an SSH tunnel — connect through the SSH key you already have, and the database port itself never needs to be reachable from outside the box at all.

ToolCostWhere it runsBest for
DBeaver CommunityFree, open sourceDesktop app (Mac/Win/Linux)Recommended default — one app, one connection tree with a folder per business, built-in SSH tunnel per connection, and it auto-draws an ER diagram from the foreign keys, which is the fastest way to actually see this schema's shape
Beekeeper Studio CommunityFree, open sourceDesktop appLighter and prettier than DBeaver if you don't need the ER diagram — same SSH-tunnel-per-connection model
SQLTools extensionFreeInside VS Code / CursorIf you want query results next to your code instead of a separate app — same editor you already deploy from
pgAdmin 4Free, self-hostedDocker container, browser-basedOnly worth it if several people need shared, no-install browser access — otherwise it's more setup than the desktop options for no real benefit here

Setting up DBeaver against orbytflow-vps, concretely:

New Connection → PostgreSQL
  Main:  host localhost · port 5432 · database mail_orbyt · user mail_orbyt
  SSH:   ☑ Use SSH tunnel
         host 200.141.5.32 · user root · auth "public key" → point at your existing key

DBeaver opens the SSH connection first, then talks to Postgres through it as if it were local — the "host" field above is localhost because, from the tunnel's far end, it is. Duplicate the connection once per business/VPS and rename each one; that's the whole multi-tenant setup. Give the DB user read-only access for exploration if you want a safety net beyond your own care with UPDATE/DELETE.

On the firewall change made this session: orbytflow-vps had Postgres/Redis/MinIO reachable on the open internet with no firewall — now closed to everything except SSH/HTTP/HTTPS. The SSH-tunnel setup above works identically whether or not that port is reachable directly, which is exactly the point: the tool never needs the database port exposed to use it.
